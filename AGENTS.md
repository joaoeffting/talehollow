# Supabase is central to this project

Auth, the database, RLS, Storage — everything backend here runs on Supabase. Before writing or changing anything that touches it (schema/migrations, RLS policies, security-definer functions, indexes, auth flows, Storage, Realtime, debugging a Postgres/RLS/auth error), load the `supabase` skill, and for anything that lives in the database specifically (tables, policies, functions, migrations, queries) also load `supabase-postgres-best-practices` before writing the SQL. This isn't optional groundwork — it's already caught real issues in this repo (e.g. the stricter `set search_path = ''` pattern used in `supabase-data-export.sql` instead of the earlier `set search_path = public`).

This project uses Supabase, never InsForge. The `insforge`/`insforge-cli`/`insforge-debug`/`insforge-integrations` skills are installed globally for a *different* project and can plausibly trigger on generic phrases like "add auth" or "add storage" — do not invoke them here under any circumstances, even if a trigger seems to match.

## Schema changes: no DB write credentials, no service-role key

There's no `SUPABASE_SERVICE_ROLE_KEY` in this project, on purpose — don't add one. Two consequences that follow from that:

- **Applying schema changes**: write the change as a standalone `supabase-<feature-name>.sql` file at the repo root (see `supabase-account-deletion.sql`, `supabase-data-export.sql`, `supabase-content-warnings.sql` for the established shape/commenting style), ask the user to run it in the Supabase SQL editor, then run `npm run gen:types` to pick up the new schema before continuing. Code that depends on a not-yet-applied column/function is expected to show a type error in the meantime — that's normal, not a bug to work around with `any`.
- **Anything needing elevated privileges** (a user deleting their own account, exporting their own data, or similar) — write a `security definer` Postgres function that captures `auth.uid()` into a local variable once and scopes every operation to that one id, granted via `grant execute on function ... to authenticated`. This is the established pattern (`delete_own_account()`, `export_own_data()`) for doing privileged operations safely without an admin key anywhere in application code.

## Git identity

Before the first commit on a fresh project, run `git config user.email` and confirm it isn't a work email carried over from the global config — check `git config --global user.email` too, since that's where it silently comes from. If it's wrong, fix it with a **local** (`git config user.email "..."`, no `--global`) override for this repo specifically; don't touch the global setting, since it may be intentional for the user's other (work) repos. Catching this before the first commit avoids a full history rewrite later — see this repo's own git history for exactly that recovery (`git filter-branch --env-filter`, a local backup branch, then a force-push), which was only needed because this wasn't caught early.

## Verifying changes: never touch the user's running dev server

If the user already has `npm run dev` running, do not kill it, restart it, or reuse its port to test something — that stops their own work without warning. Two safe alternatives, in order of preference:

1. If the change is a pure function / has no live-service dependency (e.g. a sanitizer, a pure escaping helper), verify it directly (a quick Node script, a unit-level check) instead of spinning up a server at all.
2. If a real browser/server round-trip is needed, use an isolated `git worktree` on a separate port: `git worktree add /tmp/<project>-test-wt -b test-<feature>`, copy over the changed files (or just work from a committed state) plus `.env.local` and a copy of `node_modules`, then `PORT=<other> npx next dev -p <other>` from that worktree directory. Clean up the worktree, branch, and any temp files when done. This is the only way to run a second Next.js dev server for the same project at all — Next refuses to run two instances against the same project directory even on different ports.

## Proactively check for security issues, not just when asked

Run a real security pass (leaked secrets in git history and current files, XSS via any `dangerouslySetInnerHTML`, RLS write-policy correctness, auth/admin route gating) at natural checkpoints — before a repo goes public, after shipping anything touching auth/user-generated-content/payments — not only when explicitly asked to check. In this repo, a stored-XSS hole (unsanitized chapter HTML rendered with `dangerouslySetInnerHTML`, plus a related JSON-LD script-injection issue) existed silently through several feature phases before anyone thought to ask. Use the `security-review` or `code-review` skill/slash-command for this rather than improvising the checklist each time.

## Before a portfolio repo goes public

Write a real README (what the project is, the stack, a few notable engineering decisions worth a case-study read) — not the unedited `create-next-app` boilerplate. Disclose the Claude Code-assisted workflow honestly and directly in it rather than leaving it to be discovered in commit trailers; being upfront about directing AI effectively while still catching what it gets wrong reads as a demonstrable skill, not something to hide. Add a LICENSE (all-rights-reserved by default, plus `"license": "UNLICENSED"` in `package.json`) — public visibility for portfolio/review purposes is not the same as granting reuse rights, and the two need to be stated explicitly, not implied.
